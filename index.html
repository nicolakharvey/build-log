The Build Log

A dated record of what I build and how I prove it worked.

Every entry here was working before it was written up. Each one names the build, the assurance check, the proof, and the limit. Dates are the dates things ran; nothing here is a plan or roadmap.

21 August 2026

Sandboxed safety test for a git checkpointing tool

I reviewed a local Git checkpointing tool before letting it near real work. The source had no external dependencies, no network path, no scheduler, and every destructive command behind a full typed confirmation phrase. Then I tested the safety claim in a container against four decoy repositories.

Before running the real tool, I ran a deliberately destructive fake version to prove my comparison would catch damage. It did: four failures, one for each decoy. The real tool then produced no working-tree changes.

Limits: four small decoy repositories, one run, inside a container rather than on the machine it is meant to protect.

Proof: before/after comparisons showing four failures on the fake and none on the real tool.

Backup verification by host state, not push output

A finished iPhone app had one starter-template commit while nearly eight thousand lines of screens and app state were still untracked. I swept for secrets, committed the work, made the remote private, and verified the backup by asking GitHub what it actually held rather than trusting the local push.

That changed the test I use for my project estate. A backup is not "git push succeeded." A backup is: the host reports the repo private when it should be private, the remote branch matches the local branch, there is nothing unpushed, and the files I care about are present on the host.

Limits: some repositories in the scan are scratch work, and private repositories cannot be used as public proof.

Proof: GitHub's own report: private repo, matching branch, no unpushed commits, and the app screens listed remotely.

21 August 2026

Android build verification beyond a green build

PulseMerge built as an Android app, but I checked what the build produced rather than stopping at "build succeeded." The debug APK existed and the game bundle was byte-identical inside it, but the launcher icon was 9,441 bytes while the iPhone source icon was 544,839 bytes. Capacitor had generated placeholder art, and the build system had no reason to care.

I regenerated the Android icon and splash from the game's own visual system, not from a separate design file that could drift from the product. Then I rebuilt and checked the package again. The APK moved from 4.0MB to 6.7MB, with the real branded assets present.

Limits: built and inspected, but not yet run as a played session on an Android phone.

Proof: Android debug APK built and inspected; the game files inside matched the source, and the placeholder launcher art was replaced with regenerated PulseMerge assets.

21 August 2026

Browser interaction test for pages that returned 200 but were dead

Four new web pages returned 200, passed type checks and lint, and looked correct in screenshots. They still did not work. I had served the site on one local hostname and opened it on its twin, so the framework refused to serve the scripts to that origin. A screenshot could not catch it because the static page still rendered.

The useful test was not "does the page load?" It was "can a user action change state?" I added a browser walk that clicked a control and asserted that the page responded. That caught the dead JavaScript immediately and gave me a repeatable check for this class of failure.

Limits: dev-mode origin issue only; production builds do not carry the same local-hostname behavior.

Proof: dev-server log naming the disallowed origin, plus before/after browser-walk transcripts.

Multi-agent product strategy audit

Ten product concepts came out of a chat. Instead of picking by taste, I used agents as reviewers and adversaries. Five checked claims against my repositories, two drafted rival strategies, one merged the strongest plan, and three attacked the result for weak assumptions, already-built work, and missing proof.

The useful result was not the number of agents. It was that the process treated my own machine as the source of truth. Three of the ten ideas were already built locally and unpublished, which would have been missed by a normal brainstorming pass. The run turned a loose list into a checked strategy in eighteen minutes.

Limits: one run, private live strategy, and the reviewers use the same family of models as the builders.

Proof: forty findings held privately because the output contains current strategy.

21 August 2026

Full-corpus parser audit across six years of research pages

A script pulled write-ups out of six years of weekly research documents. It appeared to work because I kept testing the same page shape. When I ran it across the full archive, 21 pages parsed as empty. The problem was human consistency: one person had written the same line four different ways over the years, and the parser only recognized one.

I changed the verification from a sample page to all 695 pages, added the missing variants, and used the archive's weekday pattern to resolve ambiguous dates where that was safe. Coverage moved from 86% to 95%.

Limits: the weekday rule is archive-specific and should not be reused as a general date parser.

Proof: before/after diff over all 695 pages, re-run from the committed script.

21 August 2026

Incentive regression test for PulseMerge

PulseMerge is meant to reward bold play more than careful play. It had passed 31 checks while doing the opposite. Three separate faults combined into one bad incentive: a multiplier was read after the move resolved, pressure paid out without effort, and the difficulty curve advanced in a way that gave cautious play the easier path.

The fix was to test the incentive as a relationship, not as isolated mechanics. I simulated a bold player and a timid player against the same rules and required the bold strategy to win. That comparison found the failure pattern that ordinary feature checks missed.

Limits: simulated players only, and the Android version has not yet been play-tested on a phone.

Proof: live PulseMerge build at muplu.com/pulsemerge, with 53 checks against the live site.

20 August 2026

Offline verification for a retiring site archive

A twenty-year-old site was being retired, so I archived 1,561 pages. The important check was not whether the archive looked fine while the old site still answered. I tested it as if the original host were already gone.

That exposed the failures a casual check would miss: lazy-loaded images saving as blanks, internal links still pointing at the old host, and a filename-shortening rule that removed the extension from the main stylesheet. That last bug would have left 673 pages rendering bare after the source disappeared.

Limits: a machine verified the structure and links; nobody manually read all 1,561 archived pages.

Proof: 35,218 internal links resolve locally and nothing points back to the old host.

Gentle daily app for Maya Foxten's audience

I built a small app for Maya Foxten's audience around one minute a day with a dog. The interaction is intentionally low-pressure: walk, press a paw into the sand, and receive one short lesson that washes up for the day. The product decision matters as much as the build. There is no punishment loop: no streak loss, no missed-day scolding, and no declining count. For this audience, the assurance work is not only technical. It is making sure the app's mechanics do not contradict the calm practice it teaches.

Limits: the audience is small, so this is still a product bet.

Proof: live app screen over the night beach, with today's practice and saved lesson card.

Build-log freshness check from commit history

I had written the rule to keep this build log current in three places, and it still fell twelve days behind. That proved the rule was not a system. I added a check that reads two factual sources: commit history across project folders, and the dates already present in the build-log page.

The check reports work days with commits and no ledger entry, and it separately reports if the ledger itself is dirty or unpushed. It includes a waiver list, because a check that complains about work I have deliberately decided not to write up will become noise and get ignored.

Limits: it only sees work that touched a tracked folder.

Proof: this page, plus the checker in ~/.claude/hooks/build-log-check.py.

19 August 2026

Lip-sync engine comparison on the same source material

Maya needed to speak, so I tested three lip-sync paths on the same still image and voice track instead of comparing demos made from different inputs. The local LTX setup kept the mouth closed in 12 of 15 samples. Seedance 2.0 articulated every sampled frame in about two minutes, at 36 credits per eight seconds. LatentSync was ported to Apple Silicon in six patches, but took 81 minutes for a 7.6-second clip and still barely moved the mouth.

The comparison gave me a production decision: use the hosted path when articulation matters, keep local experimentation alive, and do not confuse "runs locally" with "fit for this job."

Limits: LatentSync got the hardest input, so the result is evidence for this production case rather than a universal benchmark.

Proof: sampled mouth-frame strips from all three engines on the same image and audio.

19 August 2026

Medium publishing bridge with human and public-feed gates

Medium retired its publishing API, so I built a browser bridge driven over the Chrome DevTools Protocol. One command stages a complete story: title, cover image, formatted body, and draft state. It uses a dedicated browser profile, screenshots each step, and never handles credentials. If the profile is not signed in, it stops and asks for a human login.

The bridge later gained a controlled publish path: it can add topics and press publish when I explicitly schedule that, but it refuses to call the job done until the story appears in the public Medium feed. A click is not a post.

Limits: it depends on Medium's browser UI, so it is monitored and falls back to a reminder rather than silently losing a story.

Proof: the first essay it staged and the bridge code in Social Command.

18 August 2026

Provenance sweep on my own published assets

I pointed my own checker at my own website and found four published images carrying the full generation recipe in their metadata: prompts, model, settings, and other details that were invisible on the page. I cleaned and redeployed the same night.

The useful part was treating my own site as the target. AI provenance risk is easy to describe in the abstract and easy to miss in your own files. The sweep separated three different layers that people often collapse together: invisible text characters, image metadata, and marks or patterns in the pixels themselves.

Limits: metadata stripping does not remove visible watermarks or pixel-level generator marks.

Proof: the write-up The 48 characters I could not see.

18 August 2026

Clearing 1.0

Clearing is an open-source local tool for checking what goes out under your name. It finds invisible Unicode carriers in text and generation metadata in images, then removes only the parts it can honestly remove. It does not rewrite words, change pixels, or claim to defeat AI detectors.

The assurance work is in the exemptions. It leaves emoji joiners intact, preserves joiners that are spelling in Persian, Arabic, Hindi and related scripts, keeps leading byte-order marks when they are doing an encoding job, and refuses to clean verbatim archives or evidence folders. The CLI and browser page share the same core, with tests proving they do not drift apart.

Limits: image metadata checks depend on local tooling, and visible or pixel-level marks are out of scope.

Proof: github.com/nicolakharvey/clearing under MIT, with 54 zero-dependency tests.

4 August 2026

Cloud publisher for a local-first scheduler

Social Command is local-first, which means a sleeping Mac used to be a scheduling risk. I added a small Cloudflare Worker that holds only due all-auto posts inside a short horizon and publishes them at the right time. Manual and reminder posts stay local because they need a person.

The main safety rule is one writer per post. The Mac claims or withdraws a delegated job by version; while the cloud claim stands, the Mac will not publish that post. Any edit breaks the claim. "Publish now" cancels the worker's copy before publishing locally. If the worker is late, the app warns instead of racing it, because a late post is better than a duplicate post.

Limits: delegated jobs temporarily place encrypted platform tokens and media copies inside my Cloudflare account.

Proof: scheduled posts publish on time whether the Mac is awake or asleep.

18 July 2026

Scoped team portal on a local app

Social Command grew member logins without turning into a rented SaaS product. Teammates sign in over my domains, see only the brands they work on, and publish from the same calendar while the application and data stay on my machine.

The important part is that brand scope is enforced server-side, not by hiding buttons in the interface. Member sessions carry explicit brand IDs. Server routes filter brands, accounts, posts, inbox, analytics, insights, and activity before returning data. Settings, user management, and owner-only controls stay outside the member surface.

Limits: it is built for a small working team, not as a general multi-tenant SaaS platform.

Proof: in daily use by a working team across two ventures.

2 July 2026

Social Command

Social Command is my own replacement for subscription social scheduling desks: multi-brand calendar, per-platform composer, media library, analytics, engagement inbox, team access, cloud delegation, and publishing across fourteen channels. It runs on my machine, stores data in my files, and starts every account in a manual or reviewed mode until the platform setup is ready.

The value is not only that it publishes. It carries the operational checks I need: per-platform setup notes, character-limit gates, brand-crossing warnings, account-scope controls, daily backups, manual/reminder/auto modes, and a first-post visibility check because some platforms will confirm a post that only app-role users can see.

Limits: platform APIs differ, some channels require developer approval, and the local-first model means cloud publishing is deliberately narrow.

Proof: the posts and essays in this log are scheduled and published through it.
